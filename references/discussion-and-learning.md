# 共同讨论、头脑风暴与理解记录

## 学习与推进的分工

关于关键代码阅读、独立诊断、提示层次和阶段性理解证据，按需读取 [学习与独立判断](learning-and-ownership.md)。以下约定讨论节奏与头脑风暴，避免重复维护学习流程。

先确认当前任务确实涉及核心方法学习或结果解释。若用户正在设计skill、确定协作偏好或整理项目，提问应服务于流程设计和整理目标，不把参考项目的研究问题变成测验。需要从整理转入教学时，说明切换及其目的，由用户的实际请求决定。

普通工程：简述步骤的目的，自主完成已授权工作，再报告验证结果。无需逐行讲安装日志或反复提问。

核心方法、实验设计与结果解释：

1. 用具体输入、输出或一条实际轨迹讲清关键机制，定位少量真正相关的代码入口。
2. 针对当前不确定点提出一到三个问题，例如“如果动作条件有效，你预计哪个对照会下降，为什么？”或“这个结果排除了什么，尚未排除什么？”
3. 等用户回答相关问题，按实际回答补足理解；独立工程任务继续，不因讨论停下全部工作。
4. 在阶段节点记录用户展示的理解或操作证据。状态可为“已展示但未检查”“部分解释清楚”“能够解释或独立操作”；不因用户沉默或说继续就认定掌握。

问题围绕当前工作，不采用固定测验。已有证据表明用户掌握的概念无需重复检查。用户本次要求直接执行或暂缓教学时尊重其选择，在交接中留下待讲解项。

## 共同理解的具体时机

以下节点随同相关结果简报提出 1–2 个针对性问题，不等到全部执行任务结束：

- 阶段结果使当前主张更可信、受到反驳，或改变下一步取证重点时，邀请用户解释“这个结果支持或排除了什么”“哪些解释仍未覆盖”。
- 准备请求批准下一步研究方案（如扩大样本、增加新对照或调整方法）时，结合已有结果询问预期观察及其区分作用，然后单独说明需要用户决定的方案与影响。已有授权的步骤直接推进，不为制造讨论重复索要批准。

先给理解当前结果所需的简短背景，不先交付标准答案再要求复述。已有记录表明对应能力已掌握时，只讨论新增的不确定点。用户说“先不讨论”或明确本阶段暂缓教学时跳过，在交接简记待回看问题、关联证据和合适的下一次节点，不每轮重问，也不记作已经理解。

理解提问与研究授权分别处理：用户可以直接对方案作决定，不需先答对理解题；待回答只影响相关讨论，独立且已授权的工程工作继续。阶段结束前核查本阶段是否真的发起过适用的共同讨论，或已记录暂缓原因；仅在交接堆积问题不算已经触发。

## 头脑风暴的进入时机

- 主动讨论：用户说讨论 idea、找新方向、读完文献后一起想想或请专门 agent 讨论时，直接进入，不要求出现失败或瓶颈。
- 文献与复现后的综合构思：阅读一批相关论文或完成核心结果复现，已有足够材料比较机制、假设和效果时，汇总共性、差异、矛盾及尚未被检验的假设，主动提出是否进入 idea 讨论。不以阅读篇数或完成下载作为证据充分的替代，也不强制每篇论文后讨论。
- 遇到瓶颈：简述已有证据和阻塞点，先与用户讨论是否启动头脑风暴；等待期间继续独立且已授权的工作。
- 阶段结束：做简短复盘，检查是否继续支持当前主张、哪里仍缺证据。只有确有开放问题时才展开候选方案或委派专门 agent；无新问题则记录现阶段结论。

阶段结束以有意义的研究或实验阶段为单位，不是每一次工具调用。用户只要求检索、阅读或复现时，完成其交付并提出有依据的讨论入口，不自动扩大成新研究路线或新增实验。以上触发不意味着创建定时任务或常驻 agent。

## 从文献与复现形成候选 idea

先读取本项目文献索引、精读笔记和复现报告，按当前问题选取关键材料；没有读过或没有实测的内容分别标注。用以下证据链组织讨论，而非只罗列方法名：

- 文献共识与差异：各方法解决什么问题、成立条件、评价口径及最近邻工作；未对齐条件的数值不直接排名。
- 复现带来的认识：哪些作者结论得到复核，哪些差异来自实现或资源，哪些现象确实尚无解释。
- 候选机会：从机制差异、适用边界、可复用能力或解释冲突出发提出假设；可以保留当前主线，也可以探索新的问题，不以必须有“瓶颈”为前提。
- 可否证的区分：与已有工作的实质区别、支持及反对依据、最小验证与强对照、资源成本和停止条件。额外检索未完成时，新颖性标为待核实。

与用户比较候选，允许本轮结论是继续阅读、补齐复现解释或暂不提出新方法。讨论产物写入 `brainstorm.md`，实际新增实验仍需共同决定。

## 同时改进主线与审视方向

用户选择两者都做。展开头脑风暴时，分开呈现两类判断：

- **主线改进**：当前研究问题与核心主张保留，从新的文献认识、复现观察或已有瓶颈出发，提出机制、对照或证据方面的改进。说明预期收益、关键反证和最小验证成本，避免只增加模块。
- **方向审视**：检查问题是否有研究价值、最近工作是否削弱创新空间、现有证据是否持续反对核心主张、剩余资源是否足以产生可判断的结果。给出继续、收窄、暂缓或转向的建议与依据；有具体必要时提出替代方向，并说明与旧路线的区别、已有成果如何复用及转向成本。

区分实现失败、证据不足与研究主张被反驳；不因单个负结果宣布方向无价值，也不因已有投入而默认继续。材料不足时列出尚不能判断的关键问题，不虚构转向必要性。没有合理替代方向时明确说明，无需每次制造新路线。

最终对两类建议分别标明“建议／待讨论／已决定”。主流程可核查已有文献与证据并准备提案；采用新实验或改变方向由用户讨论决定。方向审视不自动终止正在执行的已授权任务。

## 专门 agent 的任务边界

使用可用的子 agent 工具，不擅自创建新的用户聊天。当前项目明确限制委派时尊重该限制；工具或授权不允许时，当前对话完成讨论并说明。

委派说明使用角色职责与输入输出，不写死特定厂商的agent配置或函数名。跨工具能力不同的处理见 [跨工具接入](portability.md)。

交给 agent 的材料只包括当前问题、相关证据入口、已失败路线及其限定范围、资源和信息约束。要求其分别完成主线改进与方向审视，寻找不同解释与可检验方案，不能为了产出新点子忽略反证。

可复用的任务说明：

> 根据给定项目问题和证据，同时完成两部分：一、在当前主线上提出少量有实质差异的改进假设；二、审视当前主线的研究价值、新颖性、反证与投入，给出继续、收窄、暂缓或转向的理由，必要时提供替代方向及成本。对值得讨论的候选给出相关工作与待核实之处、预期机制、可能失败的原因、最小验证实验、必要对照、预计资源和停止条件。区分已知事实与推断、主线改进与方向调整。不要运行实验、修改项目、部署、创建聊天、停止既有任务或替用户作研究决策；信息不足时列出需要向用户询问的问题。

主流程阅读其输出，核验关键来源，去掉已有证据否定或仅换名称的方案，再与用户比较。读文献或分析已有证据可在授权范围内完成，启动任何新增实验仍遵循主 skill 的讨论边界。

## 最小提案

每个值得讨论的候选明确：要改变哪个当前判断、与最近工作的实质区别、哪项观察会推翻它、最小实验与强对照、成本、继续／停止条件。候选创新写为待验证，不给未经支持的投稿成功概率或成果保证。

用户决定后，将采用方案和理由写入研究状态；未采用方案可简记原因与重开条件，不与当前路线并列为活跃任务。
